\# Migration Diff: 0010 to 0011 Resource Revision \& Idempotency



\## 1. Overview

This document details the structural and logical changes introduced between database migration 0010\_resource\_ontology and 0011\_resource\_revision\_idempotency. This migration is critical for establishing the event-sourcing foundation and ensuring transactional safety under high concurrency.



\## 2. Schema Changes

\### 2.1 New Table: idempotency\_records

\- Purpose: To guarantee that retrying a failed or timed-out request does not result in duplicate resource creation or state mutation.

\- Columns: 

&#x20; - idempotency\_key (VARCHAR, Primary Key): The unique identifier for the requested operation.

&#x20; - tenant\_id (UUID): Ensures idempotency is scoped strictly to the requesting tenant.

&#x20; - status (VARCHAR): Tracks the lifecycle (e.g., 'PROCESSING', 'COMPLETED', 'FAILED').

&#x20; - response\_payload (JSONB): Stores the successful response to be returned on subsequent retries.

&#x20; - created\_at / updated\_at (TIMESTAMPTZ): Bitemporal tracking of the record.



\### 2.2 Resource Revision Tracking

\- Added revision\_number (INTEGER) to core resource tables.

\- Added previous\_revision\_id (UUID) to maintain a strict, queryable history of resource state changes.

\- Implemented database triggers to automatically increment the revision\_number on any UPDATE operation.



\## 3. Row-Level Security (RLS) Updates

\- Updated RLS policies on the new idempotency\_records table to ensure that a tenant can only view or manage their own idempotency keys.

\- Added BYPASSRLS exceptions strictly for the automated background reconciliation workers, which operate under a dedicated, highly restricted service role.



\## 4. Performance Considerations

\- Indexes have been added to idempotency\_key and tenant\_id to ensure O(1) lookup times during high-throughput ingestion.

\- The response\_payload JSONB column utilizes GIN indexing to support future analytical queries on response structures without full table scans.



\## 5. Rollback Strategy

In the event of a failed deployment, the 0011\_resource\_revision\_idempotency.down.sql script will safely drop the idempotency\_records table and remove the revision tracking columns, reverting the schema to the exact state of migration 0010.
